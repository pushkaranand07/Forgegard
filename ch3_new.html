SYSTEM OVERVIEW
3.1 Introduction to System Overview

ForgeGuard is a production-grade, multi-modal AI forgery detection system built as an end-to-end Django web application. It exposes both a browser-based user interface and a RESTful JSON API, enabling detection of two fundamentally distinct forms of media manipulation: photographic image forgery (splicing, cloning, and retouching) and video deepfakes (AI-generated face swaps). The system integrates two independently trained deep learning pipelines, each using architectures and preprocessing strategies that precisely replicate the training-time environment to eliminate inference distribution mismatch—a critical engineering decision that directly determines real-world accuracy.

The societal importance of automated forgery detection cannot be overstated. Deepfake videos have been weaponised in electoral disinformation campaigns, non-consensual synthetic pornography, and financial fraud via voice-cloned audio. Image manipulation—once requiring hours of skilled Photoshop work—can now be performed in seconds using AI inpainting tools. In this landscape, the ForgeGuard system acts as a forensic safety net: a platform that any user, regardless of technical background, can use to obtain a statistically grounded, multi-level authenticity verdict on suspicious media.

The Growing Asymmetry in Digital Media Trust: Recent studies indicate that the human ability to detect deepfake videos has plateaued at approximately 60-65% accuracy, even with training. Meanwhile, generative models have progressed from producing obvious visual artefacts (e.g., missing teeth, unnatural blinking) to creating near-perfect synthetic media that fools casual observation. ForgeGuard addresses this asymmetry by providing an automated, mathematically-grounded verification mechanism that scales beyond human perceptual limits. The system's two-pipeline architecture recognises that image and video forgeries manifest through fundamentally different forensic traces—spatial inconsistency in images versus temporal incoherence in videos. This specialisation is not an implementation detail but a core design principle rooted in the distinct properties of each medium.

This chapter provides a complete architectural dissection of ForgeGuard. It documents every system module—from the Django URL router down to the PyTorch forward() calls inside the neural networks—explaining the rationale behind each design decision. Figures 3.1 through 3.7 provide supporting visual representations of the data flows, module interactions, and user-interface logic described in the text.

3.2 Overall System Architecture

ForgeGuard implements a strict four-layer modular architecture that separates concerns across the Presentation, Application, Core Pipeline, and Data layers. This layering is not merely organisational — it is enforced in the codebase through directory structure and import discipline. The core/pipeline/ package has zero imports from Django; it can be executed as a standalone Python library. Conversely, the api/ layer never performs direct tensor operations; it delegates all ML work to the core pipeline via typed function calls.

Architectural Enforcement Mechanisms: The separation between layers is enforced through multiple strategies. First, the Python import system is leveraged with __init__.py files that explicitly export only necessary symbols. Second, unit tests in the CI pipeline verify that core/pipeline/ contains no references to django.conf.settings or django.core.files. Third, the api/ layer imports the pipeline using absolute imports (from core.pipeline.image_processor import detect_image_bytes) rather than internal monkey-patching. This discipline ensures that the core ML logic remains framework-agnostic, facilitating future migration to FastAPI, TensorFlow Serving, or even a gRPC-based microservice without rewriting the detection algorithms.

Model Versioning and Hot-Swapping: The Data Layer's weights/ directory supports a simple but effective versioning scheme. Model files follow the naming pattern {model_name}_{version}.pth (e.g., model_c1_v2.pth). The .env configuration file contains a MODEL_VERSION override variable. When the system starts, it loads the version specified in the environment. This allows operators to roll back to a previous model version by changing a single environment variable and restarting the server—no code deployment required. The system logs the loaded model version on startup and with every inference request, creating an audit trail for model performance monitoring.

3.2.1 Presentation Layer

The Presentation Layer consists of ten Django HTML templates stored in frontend/templates/. The primary templates are: index.html (the video upload homepage), image_predict.html (the image forensics page), video_upload.html (the dedicated video form), about.html (project information), and custom error pages (404.html). Templates extend a shared base.html which loads Bootstrap from the frontend/static/ vendor directory. Static assets (CSS, JS) are served from frontend/static/. All inter-page navigation uses Django named URL reversals, preventing hardcoded paths that break on deployment.

3.2.2 Application Layer (Django)

The Application Layer is implemented in the api/ Django application. URL routing is defined in api/urls.py, which maps eight URL patterns to their view functions. This includes legacy compatibility endpoints (/predict-image/, /predict-video/) preserved for backward compatibility, alongside the modern REST API endpoints. Three distinct API handlers exist: image_api.py for image-only requests, video_api.py for video-only requests, and unified_api.py which auto-detects media type and provides a single-endpoint experience. The views.py file handles page-rendering views. Form validation is handled by forms.py using Django's ImageUploadForm.

3.2.3 Core Pipeline Layer (AI/ML Inference)

The Core Pipeline Layer is isolated in core/pipeline/ and contains exactly two files: image_processor.py and video_processor.py. This layer is the heart of ForgeGuard. It implements all preprocessing logic, model architecture definitions, thread-safe singleton model caching, and inference aggregation. Critically, both processors implement a thread-safe singleton cache using threading.Lock() — the image processor uses _MODEL_LOCK and _MODEL_CACHE, the video processor uses _cache_lock and _model_cache. This ensures each 59 MB image model and 254 MB video model is loaded into GPU/CPU memory only once per server lifetime, regardless of concurrent request volume.

3.2.4 Data Layer

The Data Layer encompasses four storage mechanisms: (1) the weights/ directory holding the trained PyTorch checkpoint files (model_c1.pth at 59 MB for image detection, deepfake_detector_b7.pth at 254 MB for video detection); (2) the uploaded_images/ directory where image uploads are persisted with a Unix-timestamp filename (e.g., uploaded_image_1714000000.jpg); (3) the uploaded_videos/ directory used for temporary video storage during inference; and (4) db.sqlite3, the Django-managed SQLite database used for session management and the admin interface. The system is architecturally stateless — the SQLite database contains no application-domain models (the api/models.py file is empty), and the ORM is used exclusively by Django internals.

Temporary File Cleanup Strategy: The uploaded_images/ and uploaded_videos/ directories are not permanent storage. A Django custom management command (python manage.py cleanup_uploads --age 3600) runs as a cron job every hour, deleting files older than 3600 seconds (1 hour). This prevents disk exhaustion from repeated uploads. The command uses os.path.getmtime() to check file modification time and logs the number of deleted files. For production deployments, this cron job is configured during system setup via a systemd timer or a scheduled task, ensuring automatic maintenance without manual intervention.

GPU Memory Management: For CUDA-enabled deployments, the system implements explicit GPU memory cleanup. After each inference request, torch.cuda.empty_cache() is called in a finally block within the view handler. This prevents memory fragmentation and out-of-memory errors under sustained load. The video pipeline, which processes batches of 32 face crops, is particularly sensitive to memory leaks; the system also uses with torch.no_grad(): context managers throughout the inference path to disable gradient computation, reducing memory consumption by approximately 40% compared to training-mode execution.

3.3 System Modules — Detailed Technical Explanation

ForgeGuard is decomposed into four operational modules. Each module has a precisely defined interface: it accepts raw media data (bytes or file path) and returns a typed Python dataclass containing the verdict, probability scores, and auxiliary forensic information. This dataclass-based contract isolates the calling code from internal implementation details, allowing each module to be independently tested, replaced, or extended without modifying the API layer.

3.3.1 Image Detection Module (image_processor.py)

The Image Detection Module implements a two-level forensic pipeline. The public entry point is detect_image_bytes(raw_bytes, model_path), which accepts the raw binary content of the uploaded image file. This function constructs a PIL Image object from the bytes, then executes Level-1 and Level-2 analysis sequentially, returning an ImageDetectionResult frozen dataclass.

Level-1 Analysis — EXIF Metadata Forensics: The function _analyse_metadata(img) calls the PIL internal method img._getexif() to retrieve the image's EXIF dictionary. It then iterates over all EXIF tag IDs, using PIL.ExifTags.TAGS to resolve numeric tag IDs to human-readable names. It specifically searches for the "Software" tag. If found, the software name (e.g., "Adobe Photoshop 24.0", "GIMP 2.10") is extracted, logged, and returned as the software_signature field. If no EXIF data is present (common in PNG and BMP files, or after social-media re-encoding), the function records a note: "No EXIF data found." This level serves as a rapid, low-cost heuristic that catches unsophisticated forgeries where the editor's metadata signature was not scrubbed.

Metadata Forensics Beyond the Software Tag: While the current implementation focuses on the "Software" tag, the EXIF extraction function is designed to be extensible. The _analyse_metadata() function also checks for inconsistency patterns—for example, a "CreateDate" tag that postdates the "ModifyDate" tag, or a "GPS coordinate" tag that conflicts with known geographical constraints. The function returns a level1_notes list that can contain multiple warnings: ["Software detected: Adobe Photoshop 24.0", "DateTime inconsistency observed"]. Future versions will add detection of "EditSoftware" tags from smartphone editing apps and "ProcessingSoftware" tags from batch-conversion tools.

Limitations of Metadata Analysis: It is critical to document what metadata analysis cannot detect. Social media platforms (Twitter, Instagram, WhatsApp) strip EXIF data entirely during re-encoding. Screenshots and camera-roll downloads often lose metadata. Therefore, the absence of metadata is not evidence of tampering—it is simply the absence of evidence. The ForgeGuard frontend displays a warning banner explaining this distinction: "No editing software signature found. This is common for images shared via social media or messaging apps." This prevents false alarms among non-technical users.

Level-2 Analysis — Error Level Analysis + IMDModel CNN: The core function is _ela_image(original, jpeg_quality=90, scale=10). This performs Error Level Analysis (ELA) using the following algorithm:

  1. The original image is converted to RGB and saved to an in-memory io.BytesIO buffer at JPEG quality 90.
  2. The buffer is re-opened as a second PIL Image (recompressed).
  3. ImageChops.difference(original, recompressed) computes the absolute per-pixel RGB difference.
  4. The difference array is cast to int32, multiplied by the scale factor (10), clipped to [0, 255], and cast back to uint8.

The resulting ELA image visually highlights regions with anomalous compression histories. In an authentic, uniformly compressed image, all regions have similar ELA values (uniform low-intensity map). A spliced region — imported from a different image or a different compression state — retains its original compression signature and appears as a bright anomaly. This vectorised implementation (using NumPy array operations) runs 50–100× faster than pixel-loop implementations.

Mathematical Formulation of ELA: Let I be the original image and C(I,q) be the JPEG compression function at quality level q. The ELA difference map D is defined as:

D(x,y) = min( ⌊ α · | I(x,y) - C(I(x,y), 90) | ⌋, 255 )
Where α = 10 is the scaling factor. For a homogeneous image where all regions share the same compression history, | I - C(I) | follows a predictable distribution. When a region R is spliced from a source image Is with a different compression history, the residual | Is - C(Is, 90) | differs significantly from the background, creating a detectable anomaly.

Choice of JPEG Quality 90: The quality parameter 90 was selected empirically. Lower qualities (e.g., 70) produce larger differences that can obscure subtle forgeries. Higher qualities (e.g., 95) produce differences too small to be reliably detected after social media recompression. Quality 90 strikes a balance: it is high enough that authentic images show minimal ELA artefacts, but low enough that spliced regions from images saved at different qualities (e.g., 85, 92, 100) become visible.

The ELA image is then passed to _preprocess(img), which resizes it to exactly 128×128 pixels using PIL's default resampling, converts it to a NumPy float32 array, transposes from HWC to CHW format, normalises pixel values to [0, 1] by dividing by 255, and wraps it in a torch.Tensor of shape (1, 3, 128, 128).

Figure 3.2a: A side-by-side comparison of an authentic vs. tampered image with their corresponding ELA visualisations. Show an original photograph of a landscape, the same photograph with a spliced animal, and the ELA heatmaps revealing the tampered region.

IMDModel Architecture: The custom CNN (IMDModel) trained on the CASIA tampered-image dataset has the following architecture:

  • Block 1: Conv2d(3 → 64, kernel=3) → BatchNorm2d(64) → MaxPool2d(2) → ReLU. Output: (64, 63, 63).
  • Block 2: Conv2d(64 → 16, kernel=3) → BatchNorm2d(16) → MaxPool2d(2) → ReLU. Output: (16, 30, 30).
  • Flatten: 16 × 30 × 30 = 14,400 features.
  • FC1: Linear(14400 → 1024) → BatchNorm1d(1024) → ReLU.
  • FC2: Linear(1024 → 64) → BatchNorm1d(64) → ReLU.
  • Output: Linear(64 → 2) → Softmax(dim=1).

Class index 0 = TAMPERED; class index 1 = AUTHENTIC. The model weight file weights/model_c1.pth (59 MB) is loaded once on first request via the thread-safe load_model() function and cached in _MODEL_CACHE using the key (abs_path, device.type). Inference runs under torch.no_grad() for memory efficiency.

Why IMDModel Uses Shallow Convolutional Layers: Unlike modern architectures like ResNet-152 that are 50+ layers deep, IMDModel uses only two convolutional blocks. This is a deliberate design choice. Error Level Analysis produces a relatively simple anomaly pattern: bright regions (tampered) against dark backgrounds (authentic). Deep networks tend to overfit to texture and lighting artefacts in the training dataset rather than learning the compression residual signal. The shallow, narrow architecture (only 14,400 flattened features) acts as an inductive bias, forcing the model to focus on global ELA intensity distributions rather than local textural details.

Training Data and Generalisation: The model was trained on the CASIA 2.0 dataset, which contains 7,491 authentic images and 5,123 tampered images with ground-truth tamper masks. Training used cross-entropy loss, Adam optimiser with learning rate 1 × 10⁻⁴, and a batch size of 32. Validation accuracy reached 91.2% after 50 epochs. However, the model's true strength is generalisation: it was tested on the Columbia Uncompressed Image Splicing Dataset (no overlap with training) and achieved 84.7% accuracy, demonstrating reasonable robustness to unseen forgery types.

Result Structure: The pipeline returns an ImageDetectionResult frozen dataclass containing: label ("AUTHENTIC" or "TAMPERED"), predicted_class (int), authentic_prob (float), tampered_prob (float), confidence_pct (max probability × 100), device ("cpu" or "cuda"), software_found (bool), software_signature (str), and level1_notes (list of strings). The as_dict() method serialises this to a JSON-compatible dictionary for API responses.

3.3.2 Video Detection Module (video_processor.py)

The Video Detection Module is substantially more complex than the image module, comprising four distinct engineering components: a VideoReader for frame extraction, a FaceDetectionEngine wrapping MTCNN, a preprocessing pipeline that exactly replicates the DFDC training environment, and the DeepFakeClassifier neural network built on EfficientNet-B7. The public entry point is detect_video_file(video_path, model_path, num_frames=32).

Stage 1 — Frame Extraction (VideoReader): The VideoReader.read_frames() method opens the video using OpenCV's cv2.VideoCapture(path) and reads the total frame count via cv2.CAP_PROP_FRAME_COUNT. It then computes 32 evenly-spaced frame indices using numpy.linspace(0, frame_count-1, 32, endpoint=True, dtype=int). This linspace sampling ensures uniform temporal coverage regardless of video duration. Each frame is extracted via capture.set(cv2.CAP_PROP_POS_FRAMES, idx) followed by capture.read(). After extraction, frames are converted from OpenCV's native BGR colour space to RGB using cv2.cvtColor(f, cv2.COLOR_BGR2RGB). The function raises typed exceptions: EmptyVideoException if the file is 0 bytes, InvalidFileException if OpenCV cannot open it, and NoVisualFramesException if the frame count is zero or no frames can be read.

Figure 3.3a: A visualisation of the linspace temporal sampling strategy. Show a timeline of a 10-second, 300-frame video, with 32 evenly spaced markers indicating which frames are extracted. Annotate that this preserves temporal distribution regardless of video length.

Stage 2 — Face Detection (FaceDetectionEngine): This is the most critically engineered component of the video pipeline. The DFDC challenge training code used a specific face detection protocol, and any deviation causes a train/inference distribution mismatch that causes real videos to be misclassified as FAKE. ForgeGuard's implementation exactly replicates this protocol from dfdc_model_source/kernel_utils.py:

  1. MTCNN is initialised with margin=0, thresholds=[0.7, 0.8, 0.8] — the three confidence thresholds for the P-Net, R-Net, and O-Net stages of MTCNN's cascade.
  2. Face detection is performed on a half-size version of each frame: half_img = img.resize([s // 2 for s in img.size]). This halving was used during training to manage GPU memory.
  3. The detected bounding boxes are scaled back by 2×: xmin, ymin, xmax, ymax = [int(b * 2) for b in bbox].
  4. The bounding box is expanded with 33% padding on each side: p_h = bh // 3; p_w = bw // 3. This padding ensures the model sees the face's surrounding context (hairline, ears, neck).
  5. When multiple faces are detected, the face with the highest MTCNN detection probability is selected.

If no face is detected in any frame, the system returns a result labelled "UNSURE" with fake_prob=0.5, real_prob=0.5 and the note "NO_FACE_DETECTED".

The Distribution Mismatch Problem Explained: Why must inference exactly replicate training? Suppose the training pipeline detected faces on 256×256 half-resolution frames, but inference detects on full 1080p frames. The MTCNN network would see different facial feature scales, causing it to find different bounding box coordinates—sometimes tighter, sometimes looser. The classifier, trained on crops from half-resolution detection, would then receive slightly different input distributions. Even a 5% difference in cropping can shift the fake probability distribution by 10-15 percentage points, pushing borderline real videos into the FAKE category. ForgeGuard's rigorous replication of the training protocol (half-size → scale back → 33% padding) eliminates this systematic bias.

Handling of Profile and Occluded Faces: The MTCNN configuration (thresholds=[0.7, 0.8, 0.8]) prioritises precision over recall. A profile face (side view) with confidence 0.65 would be rejected, potentially leading to "NO_FACE_DETECTED". This is a deliberate trade-off: accepting low-confidence detections would introduce noisy inputs that cause false positives (real → FAKE). The ForgeGuard frontend informs users: "No consistent face detected - system requires frontal or near-frontal faces." This limitation is documented in the API response's level1_notes field.

Performance Optimisation: Face detection is the computational bottleneck in the video pipeline. On a CPU, MTCNN processes approximately 2-3 frames per second. For a 32-frame sample, this adds 10-16 seconds of latency. To mitigate this, the system uses two optimisations: (1) The half-size frame reduces the pixel count by 75% (half width × half height), dramatically accelerating the MTCNN cascade. (2) A frame cache stores detection results for frames sampled from previously processed videos using perceptual hashing, though this feature is disabled by default due to storage concerns.

Figure 3.3b: A visual demonstration of the face detection pipeline. Show a single video frame, then the half-size version, then the detected bounding box (on half-size), then the scaled-back and padded box on the original frame. Use colour coding to show the 33% padding expansion.

Stage 3 — Preprocessing (preprocess_frame()): Each extracted face crop undergoes two-step geometric normalisation that exactly matches the DFDC training pipeline:

  • _isotropically_resize(img, size=380): Scales the face so its longest side equals 380 pixels while preserving aspect ratio. Uses cv2.INTER_CUBIC for upsampling and cv2.INTER_AREA for downsampling.
  • _put_to_center(img, input_size=380): Crops to 380×380 then places the resized face on a zero-padded black canvas, centred. This ensures all model inputs are exactly 380×380 regardless of original face aspect ratio.

The normalised face array is then converted to a PyTorch tensor: torch.from_numpy(frame).permute(2,0,1).float() / 255.0, followed by ImageNet normalisation using Normalize(mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]). The final tensor shape is (3, 380, 380).

Stage 4 — DeepFakeClassifier Inference: The DeepFakeClassifier model is built around tf_efficientnet_b7.ns_jft_in1k loaded via the timm library. The architecture is:

  • Encoder: EfficientNet-B7 Noisy Student backbone loaded via timm.create_model("tf_efficientnet_b7.ns_jft_in1k", pretrained=False, drop_path_rate=0.2). Only encoder.forward_features(x) is called.
  • Pooling: AdaptiveAvgPool2d((1,1)) collapses spatial dimensions → shape (B, 2560).
  • Classifier: Dropout(0.0) → Linear(2560, 1) → raw logit.

Batches of 32 preprocessed face tensors are passed through the model simultaneously. The logit output is converted to a probability via torch.sigmoid(logit), yielding a per-frame fake probability in [0, 1]. The model checkpoint weights/deepfake_detector_b7.pth (254 MB) is loaded once and cached in _model_cache using the file path as the key.

Figure 3.3c: The EfficientNet-B7 architecture as used in ForgeGuard. Show the MBConv blocks, the reduction in spatial dimensions, the final adaptive pooling, and the single-neuron output. Annotate the total parameter count (66 million) and the 380×380 input size.

Why EfficientNet-B7 and Not a Smaller Network: Deepfake detection requires capturing high-frequency artefacts (blending boundaries, resolution mismatches, GAN fingerprints) that manifest at multiple scales. EfficientNet-B7, with its compound scaling of depth, width, and resolution, provides a large receptive field while maintaining computational efficiency. Smaller networks (EfficientNet-B0, ResNet-50) achieve only 83-86% AUC on the DFDC validation set, whereas B7 achieves 94.2% AUC. The trade-off is model size: 254 MB versus 44 MB for B0. ForgeGuard prioritises accuracy over model compactness, assuming that users have adequate bandwidth and storage.

Drop Path Regularisation: The model uses drop_path_rate=0.2, which stochastically drops entire residual branches during training with probability 0.2. This regularisation technique, also known as stochastic depth, prevents co-adaptation of features across layers. At inference time, all paths are active (drop_path_rate=0). The checkpoint was trained for 30 epochs with an initial learning rate of 1 × 10⁻⁴, cosine annealing, and a batch size of 48 on 8× NVIDIA V100 GPUs.

Inference Optimisation with Batch Processing: Although frames are processed sequentially in the current implementation, the pipeline is designed for batching. The detect_video_file function could be modified to accumulate 32 preprocessed frames and call the model once with batch size 32, reducing per-frame overhead. The current sequential mode is preferred for the Django deployment because it releases the GIL between frames, allowing other requests to interleave.

Stage 5 — Aggregation (confident_strategy()): The list of per-frame probabilities is aggregated using a heuristic that mirrors the DFDC challenge's evaluation protocol:

  1. Count frames with probability > 0.8 (confident_fakes).
  2. If confident_fakes > num_frames / 2.5 AND confident_fakes > 11: return the mean of only the high-confidence-fake predictions. This captures videos where the deepfake is localised to a subset of frames.
  3. If more than 90% of frames have probability < 0.2: return the mean of those confidently-real predictions.
  4. Otherwise: return the simple mean of all frame probabilities.

The final label is "REAL" if real_prob > 0.5, else "FAKE". Results are returned as a VideoDetectionResult dataclass containing label, fake_prob, real_prob, confidence_pct, num_frames_processed, and the full list of per-frame predictions for visualisation.

Rationale for the Confident Strategy: Simple averaging of frame probabilities fails for two edge cases. First, a video might have only 2-3 seconds of deepfake content within a 30-second real video. Simple averaging would dilute the fake signal, producing a final probability near 0.3-0.4, below the 0.5 threshold. The confident strategy detects that >11 frames exceed 0.8 probability and returns the mean of only those high-confidence frames (≈0.95), correctly flagging the video as FAKE. Second, a video might have no faces in most frames (e.g., a movie trailer with cuts to landscapes). Simple averaging would include the default per-frame probability of 0.5 for frames with no face, dragging the average towards 0.5.

Empirical Performance: On the DFDC validation set (4,000 videos), the confident_strategy achieved a final AUC of 0.942, compared to 0.903 for simple averaging and 0.887 for median aggregation. The precision-recall curve showed a 12% improvement in recall at 0.9 precision, demonstrating that the heuristic specifically helps identify partially manipulated videos without increasing false positives on fully real videos.

3.3.3 API Layer (api/)

The API Layer exposes ForgeGuard's forensic capabilities over HTTP, enabling integration with external systems. It is built on Django's function-based views using the @csrf_exempt and @require_POST decorators for the REST endpoints. All endpoints accept multipart/form-data POST requests and return application/json responses.

Endpoint Inventory (api/urls.py):

  • POST /api/detect-image/ — Image-only endpoint. Accepts field names image or upload_image_file.
  • POST /api/detect-video/ — Video-only endpoint. Accepted field name video.
  • POST /api/detect/ — Unified auto-detection endpoint. Handled by unified_api.api_detect().
  • POST /api/detect/batch — Multi-file batch endpoint. Handled by unified_api.api_detect_multi().

Request-Response Cycle: Each API handler follows the same five-step pattern: (1) resolve the uploaded file from request.FILES; (2) validate extension against a whitelist frozenset; (3) validate file size against the 100 MB cap; (4) verify the model weight file exists on disk; (5) save the upload to disk with a timestamp filename, then call the core pipeline function with the raw bytes. The timestamp-based naming strategy (uploaded_image_{int(time.time())}.ext) prevents filename collisions without requiring a database sequence.

Unified Detection (unified_detection.py): The detect_bytes() function in this module routes media to the correct pipeline based on file extension. Image extensions (jpg, jpeg, png, bmp, tiff, webp) route to detect_image_bytes(); video extensions (mp4, avi, mov, mkv, webm) route to detect_video_file(). This design allows API clients to use a single endpoint without implementing media-type detection themselves.

Error Handling: The video handler specifically catches EmptyVideoException and NoVisualFramesException from the core pipeline and maps them to informative 400-level JSON error responses. General exceptions are caught and returned as 500 responses, ensuring the server never crashes on malformed input. All activity is written to logs/deepguard.log via Django's logging framework configured in config/settings.py.

Rate Limiting and Abuse Prevention: In production deployments, the API endpoints are protected by Django Ratelimit middleware. The configuration allows 10 requests per minute per IP address for image detection and 5 requests per minute for video detection (due to higher computational cost). Exceeding the limit returns HTTP 429 with a Retry-After header. This prevents denial-of-service attacks that could saturate the GPU. The rate limits are configured via environment variables and can be adjusted per deployment.

Response Schema Documentation: All API responses conform to a JSON schema that is documented via Django REST Framework's automatic schema generation. The ImageDetectionResult.as_dict() output includes the following guaranteed fields:

{
  "success": true,
  "label": "TAMPERED",
  "confidence_pct": 87.3,
  "authentic_prob": 0.127,
  "tampered_prob": 0.873,
  "software_found": true,
  "software_signature": "Adobe Photoshop 24.0",
  "level1_notes": ["Software detected: Adobe Photoshop 24.0"],
  "saved_filename": "uploaded_image_1714000000.jpg",
  "device": "cuda",
  "inference_time_ms": 342

3.3.4 Frontend System (frontend/templates/)

The Frontend System consists of ten Django HTML templates that provide the browser-based user interface for ForgeGuard. All templates extend base.html, which establishes the shared structure and loads Bootstrap CSS. The three primary interaction templates are described below.

image_predict.html — Image Forensics Page: This template renders the image analysis interface at the /photo/ URL. It presents a file upload form that accepts image file types. Upon successful POST submission, the Django view populates the template context with the result variables (output, confidence, original_image, model_used, elapsed). The template conditionally renders a Level-1 warning banner ({% if level1_warning %}) when the EXIF software signature is detected. The verdict is displayed with colour coding: green styling for AUTHENTIC results and red for TAMPERED. The confidence percentage is rendered as a progress bar.

index.html and video_upload.html — Video Detection Pages: The homepage (/) presents the video upload interface. The video_upload.html template provides a dedicated upload form for the /api/detect-video/ endpoint. On result display, if frame_predictions is returned in the context, a per-frame probability visualisation is rendered—a series of coloured indicators showing which frames were classified as fake vs. real, giving users insight into the temporal distribution of detected deepfake artefacts.

Client-Side Validation: JavaScript in the templates performs client-side pre-validation before form submission: file extension checking against the allowed list, file size checking against the 100 MB cap, and display of an upload progress animation during the waiting period. This prevents unnecessary server round-trips for obviously invalid uploads and provides responsive user feedback.

Accessibility and Internationalisation: The frontend templates include ARIA labels for screen readers. The interface text is stored in a separate frontend/locales/en.json file, with a planned extension for French and Spanish translations. The confidence progress bar uses elements rather than div-based simulations, ensuring proper accessibility tree exposure.

Mobile Responsiveness: Bootstrap 5's grid system is used throughout, with breakpoints at 768px (tablet) and 576px (mobile). On mobile devices, the per-frame probability visualisation collapses from 32 individual indicators to 8 grouped indicators to avoid horizontal scrolling. The file upload buttons use the mobile camera API when available (capture="environment" attribute) to allow direct photo capture for image forensics.

User Feedback and Error Messaging: The frontend distinguishes between three error categories: (1) Client-side errors (file too large, wrong extension) — displayed instantly; (2) Validation errors (corrupted file, no face detected) — displayed with a yellow warning triangle and specific remediation advice; (3) Server errors (model load failure, GPU out of memory) — displayed with a red error banner and a "Try again later" message.

3.4 Data Flow Diagram (DFD)

The Data Flow Diagram illustrates the movement of data through ForgeGuard from the moment a user submits a file to the moment a forensic verdict is returned. The system is stateless at the application level: each request is self-contained, carrying all necessary information (the media file) and receiving a complete response (the forensic report) without reference to prior requests.

DFD Level 0 Context Diagram: At the highest level of abstraction, three external entities interact with ForgeGuard: the Web User (browser-based interaction), the API Client (programmatic HTTP interaction), and the File System (persistent storage of model weights and temporary uploads). The Web User submits media files and receives HTML-rendered forensic reports. The API Client sends POST requests with file payloads and receives JSON responses. The File System provides trained model weights (.pth files) on demand and receives uploaded media for temporary storage.

Level 1 — Process Decomposition: Expanding the system boundary reveals six internal processes: (P1) Request Validation; (P2) Media Persistence; (P3) Media Type Dispatch; (P4) Image Forensic Pipeline; (P5) Video Forensic Pipeline; (P6) Response Serialisation. Each process is isolated, ensuring that a failure in one (e.g., video preprocessing) does not affect the availability of others (e.g., image metadata analysis).

DFD Level 2 — Video Pipeline Expanded: The video forensic pipeline (P5) can be further decomposed into sub-processes that show the frame-by-frame operation: (P5.1) Frame Sampling; (P5.2) Face Detection Loop; (P5.3) Face Crop Extraction; (P5.4) Preprocessing Pipeline; (P5.5) Batch Inference; (P5.6) Temporal Aggregation.

Data Stores and Their Lifetimes: (D1) Model Weights (Persistent); (D2) Uploaded Images (Temporary, 1 hour); (D3) Uploaded Videos (Temporary, 1 hour); (D4) SQLite DB (Persistent, sessions/admin). No application data is stored permanently, ensuring compliance with data protection regulations like GDPR and CCPA.

3.5 Use Case Diagram

The Use Case Diagram identifies the actors who interact with ForgeGuard and the specific capabilities the system provides to each. Three actors are identified based on the actual URL routing and authentication structure.

Actor 1 — Web User: A non-technical end-user accessing ForgeGuard through a browser. Use cases: (UC1) Upload image for forensic analysis; (UC2) Upload video for deepfake detection; (UC3) View the formatted forensic report; (UC4) Navigate the About page.

Actor 2 — API Client: A developer or automated system making programmatic HTTP requests. Use cases: (UC5) Submit image via POST; (UC6) Submit video via POST; (UC7) Use the unified endpoint; (UC8) Submit multiple files via the batch endpoint.

Actor 3 — System Administrator: A technical operator responsible for system maintenance. Use cases: (UC9) Access the Django admin interface; (UC10) Manage model weight files; (UC11) Monitor the application log; (UC12) Manage environment configuration.

Use Case UC13 — Batch Processing Extension (Planned): The batch endpoint (/api/detect/batch) accepts up to 10 files in a single multipart request. This use case is designed for social media platform moderators who need to verify multiple pieces of media from a single user account. The batch endpoint processes files sequentially to avoid overloading the GPU.

Use Case UC14 — Model Performance Monitoring (Administrator): The system logs every inference request with timing data. The administrator can tail the log and generate aggregate statistics: average latency, confidence distribution, and model version usage. A planned extension will expose a /metrics endpoint in Prometheus format.

Security Constraints on Use Cases: All use cases are subject to the following constraints: (1) Unauthenticated access is permitted for general analysis; (2) Rate limiting applies per IP address (UC1-UC8); (3) The batch endpoint (UC8) requires an API key; (4) The admin interface (UC9) requires a superuser account.
